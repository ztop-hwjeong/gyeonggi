# Design System

[디자인 개요](../DESIGN.md) · [기초 스타일](foundations.md) · [컴포넌트](components.md) · [사용 패턴](patterns.md)

비즈렌즈 디자인 시스템은 값·형태·동작·조합·검증을 연결하는 공통 계약이다. 토큰만 공유하거나 화면마다 같은 모양을 다시 그리는 방식으로 운영하지 않는다. 현재는 문서와 화면을 함께 검토하는 단계이며, 실제 앱의 공통 컴포넌트 구현은 아직 없다.

## Layers and Sources

| 계층 | 책임 | 기준 원본 |
|---|---|---|
| 방향 | 사용자를 대하는 태도·시각적 성격·문서 경계 | `DESIGN.md` |
| 기초 | 색상 역할·서체·간격·형태·아이콘 | `foundations.md` |
| 값 | 기본 값과 의미 역할의 연결 | `design-tokens.json` |
| 구현 변수 | 값 원본에서 파생한 CSS 변수 | `tokens.css` |
| 컴포넌트 | 한 부품의 크기·상태·입력·행동·접근성 | `components.md`와 향후 앱 공통 코드 |
| 패턴 | 여러 부품의 순서·위계·조건·결과·복구 흐름 | `patterns.md` |
| 대화 | 공통 부품을 대화와 보조 작업에 적용하는 규칙 | `ai-conversation.md` |
| 모션 | 누름·등장·퇴장·반복 조작·동작 줄이기의 계약 | `motion.md` |
| 카탈로그 | 상태별 단독 예시·조합 예시·반응형 검증 | 검토 화면과 향후 컴포넌트 카탈로그 |

값은 토큰 원본에서만 바꾼다. 역할과 사용 조건은 해당 문서에서 정의하고, 구현은 그 계약을 따른다. 파생 CSS에 별도 값을 추가하거나 문서마다 같은 규격을 다시 정의하지 않는다. 임시 검토 자산은 공통 디자인 규칙의 원본으로 취급하지 않는다.

## Component Contract

공통 부품을 만들 때 다음 항목을 한 단위로 정의한다.

| 항목 | 정의할 내용 |
|---|---|
| 목적과 경계 | 어떤 문제에 쓰며, 어떤 경우 다른 부품을 선택하는지 |
| 구조 | 라벨·아이콘·내용·보조 영역의 위치와 정렬 |
| 변형 | 주요·보조 강조, XS·S·M·L 등 허용한 크기 |
| 입력과 출력 | 선택값·비활성·오류·로딩 등 입력 상태와 사용자 동작의 결과 |
| 행동 | 열기·닫기·선택·제출·중단·포커스 이동 등 실제 상호작용 |
| 접근성 | 이름·역할·상태 전달, 키보드 조작, 터치 영역 |
| 경계 상태 | 빈 값·긴 한글·여러 줄·글자 확대·좁은 화면 |
| 예시와 확인 | 기본 상태뿐 아니라 실패·복구와 다른 부품의 조합 |

컴포넌트의 색·크기는 역할 토큰으로 고른다. 화면에서 임의의 색상·모서리·간격을 넘겨 외형을 계속 바꾸는 사용법을 기본 API로 제공하지 않는다. 실제로 필요한 변형은 이름을 붙여 공통 규격에 추가한다.

## Initial Inventory

| 묶음 | 공통 부품 | 함께 검토할 동작 |
|---|---|---|
| 실행 | 버튼·아이콘 버튼 | 강조 수준·중복 실행·로딩·비활성 |
| 입력 | 필드·텍스트 입력·여러 줄 입력·선택 상자 | 라벨·도움말·검증·키보드 선택 |
| 선택 | 체크박스·라디오·스위치·필터 Chip | 값 변경·선택 해제·그룹 관계 |
| 탐색 | 메뉴·탭·분할 선택 | 현재 위치·포커스·보기 변경 |
| 정보 | 내용 행·속성 행·표·범례 | 정렬·선택·긴 값·데이터 없음 |
| 피드백 | 인라인 안내·토스트·메뉴·확인창 | 실패 범위·재시도·닫기·포커스 복귀 |
| 조합 | 조회 영역·결과 도구·본문과 보조 패널·대화 입력 | 조건 적용·결과 갱신·패널 열기·입력 보존 |

이 목록은 화면에 제공할 제품 기능 목록이 아니라, 일관성을 유지하기 위한 공통 UI 범위다. 앱에 필요하지 않은 부품을 미리 모두 구현하지 않는다.

## Catalog and Verification

앱의 공통 컴포넌트 카탈로그는 [Storybook](https://storybook.js.org/docs)으로 구축한다. 상태별 예시·문서·상호작용 검증을 같은 카탈로그에서 관리한다. 현재는 앱 공통 컴포넌트가 없는 문서·검토 화면 단계이며 Storybook은 설치되지 않았다. 별도 HTML을 다시 만드는 방식은 검토 단계까지로 제한하고, 앱 구현 이후에는 카탈로그와 앱이 같은 부품을 사용한다.

- 단독 예시는 크기·강조·기본·호버·포커스·비활성·로딩·오류를 확인한다. 해당하지 않는 상태는 억지로 만들지 않는다.
- 조합 예시는 조건 → 실행 → 결과, 입력 → 실패 → 수정, 질문 → 응답 → 중단·재시도의 의미 있는 행동을 확인한다.
- 화면 검토는 PC·좁은 화면·글자 확대, 긴 한글·숫자·줄바꿈, 입력기 조합 중 Enter를 포함한다.
- 색상 대비·역할·포커스·키보드·조작 영역을 유지하면서 실제로 읽기 편한지도 렌더링된 화면에서 확인한다.
- 시각 비교는 실제 화면 기준을 유지하는 데 사용한다. 픽셀 일치가 목적이 되어 의도한 개선까지 막지 않으며, 구성이나 동작을 바꿨으면 해당 예시도 함께 갱신한다.
- 아이콘은 채택한 Phosphor의 같은 크기·같은 역할을 유지하고 Regular·Fill·작은 크기에서의 식별성을 확인한다. 모션은 정상 재생뿐 아니라 빠른 반복 조작·중간 취소·설정 변경 후의 최종 상태를 확인한다.

## Change Rules

1. 먼저 기존 부품·패턴·토큰으로 표현 가능한지 확인한다.
2. 한 화면의 특수한 내용이면 화면 구성으로 해결하고, 여러 곳에 반복되는 문제이면 공통 변형을 검토한다.
3. 새 규격은 목적·기존 규격으로 부족한 이유·적용 범위를 함께 정의한다.
4. 값·부품·문서·관련 예시를 같은 변경에서 맞추고 의미 있는 동작과 실패 경로를 확인한다.
5. 기존 사용처에 영향을 주는 변경은 사용처를 확인하고 함께 수정한다. 사용하지 않는 호환 변형을 무조건 남기지 않는다.
6. 표면·경계·호버·포커스 피드백은 같은 역할의 부품을 나란히 확인한다. 입력창을 수정하면 검색·선택 상자·여러 줄 입력·대화 입력과 조회 영역 안의 사용처까지 함께 검토한다. 개별 화면의 덮어쓰기로 규칙을 갈라놓지 않는다.

국내 레퍼런스는 부위별 판단 근거로 연결한다. 사이트 이름만 적고 출처의 목적과 다른 모양을 임의로 채택하지 않는다. 실제 화면 검토에서 합의된 기준은 기초·부품·패턴 중 해당 계층에 반영한다.
